# Bug scan, 2026-08-27

A deliberate hunt for latent bugs, run immediately after `docs/104`'s
steps 1 and 2 shipped. Three findings, two of them in that just-shipped
code. Two are fixed; the third is recorded, not fixed.

Worth noting up front what did *not* find these: `tsc` passes on every
one of them, and the 156-test suite passes on every one of them. All
three came from reading the code against what the database actually
contains.

## 1. A fallback source could never refresh its own data — FIXED

**Severity: real, silent, and permanent until noticed.**

`docs/104` step 1 gave the fallback this write condition:

```sql
AND (name IS NULL OR name_source IS NULL)
```

A row the fallback itself wrote on an earlier run satisfies neither
branch — it has a name, and it has provenance (its own). So the fallback
skipped it. **Every name a fallback source wrote froze permanently at
whatever the first attributed run produced**, and would never pick up an
upstream rename, correction, or withdrawal again. Nothing would report
this: the source still runs, still reports thousands of rows "ingested",
and the stale rows look exactly like fresh ones.

This was introduced *by the fix* for the previous bug — that fix added
`name_source IS NULL` so a fallback could adopt its own unattributed
rows, and stopped one condition short of letting it keep them current.

**Fix**: a third branch, `OR name_source = <this source's own id>`. The
source can refresh what it owns, while a row belonging to the primary
still fails all three branches, so the "a fallback never overwrites the
primary" rule is untouched.

**Verified** against the real table, inside a transaction that rolled
back: a row set to `name_source = 'ripe-asn-names'` matched the old
condition **0** times and the new condition **1** time, while rows owned
by `caida-asn-names` matched the new condition **0** times.

## 2. Provenance columns hold ingester tags, not registry source ids — GUARDED

**Severity: would delete an entire table.**

These columns look like they store the source id. They do not — they
store whatever tag the ingester chose, via
`source.config.source ?? source.config.id`. Real divergences in the
current codebase:

| Registry id | What actually lands in the column |
|---|---|
| `feodotracker` | `abuse.ch-feodotracker` |
| `gcp-ip-ranges` | `gcp` |
| `ris-whois-ipv4` / `ris-whois-ipv6` | same (no override — today) |

Any cleanup logic that compares a registry id against one of these
columns therefore either matches nothing or matches everything.
`docs/104` step 2 walked straight into this: the first version compared
`bgpOriginSource` (a *project* name, `"ripe-ris"`) against the column,
which would have deleted all 1.6M rows. That was caught before running,
and fixed with an explicit project→ids map.

But the map is only correct **by accident**: `ingestRisWhoisDump` happens
to write a plain `config.id`. Add a `source:` override to those two
registry entries — a one-line change, and a pattern other sources already
use — and the purge silently becomes "delete everything".

**Fix**: a hard invariant on the destructive operation. Before deleting
"everything except X", count the rows that X should be keeping; if that
count is zero, refuse and warn instead. Zero means either the selected
sources wrote nothing or the ids don't match the column, and neither
justifies deleting the remainder.

**Verified**: with the table's tags deliberately renamed, the check's
count query returns 0 (so the purge refuses). With normal tags and 500
seeded deselected-project rows, the purge still fires correctly —
`cleared: 500`, the 1,564,709 real rows untouched.

## 3. A source removed from the registry orphans its rows forever — NOT FIXED

**Severity: latent. Real, but nothing triggers it today.**

Every per-source table follows the same refresh pattern: delete *my own*
rows, then reinsert. `geofeed_ranges`, `cloud_ranges`, `threat_ranges`,
`anonymity_ranges`, `verified_bot_ranges`, `rpki_roas`,
`bgp_origin_ranges`, `abuse_contacts`, `network_names`.

That is correct for a source refreshing itself, and wrong for a source
that stops existing. Delete a registry entry — one of the 178 verified
geofeeds whose certificate broke, say — and nothing ever deletes its
rows, because the only code that would have is the entry just removed.

This matters most for `geofeed_ranges` specifically: it is the
highest-confidence geo layer, so a stale operator claim doesn't sit
harmlessly in a table, it *wins* the resolution and answers queries ahead
of a fresh inferred city.

`docs/104`'s two purges fix the two *configurable* instances of this. The
general case — a source removed from the registry outright — is unfixed
everywhere.

**Checked empirically, and the check was inconclusive**: no orphans found
in the sandbox database. That is not evidence of absence — most of those
tables are near-empty there because only a handful of sources have ever
been run against it. The finding rests on the code, not on that query.

**Not fixed deliberately.** A general "delete rows whose source is not in
the registry" sweep is a destructive operation aimed at every table at
once, and finding 2 above is precisely why that is dangerous: it would
have to compare registry ids against columns that demonstrably do not
contain registry ids. Doing it safely needs the tag/id relationship made
explicit first — the same map-and-verify shape `BGP_ORIGIN_SOURCE_IDS`
uses, generalised. Worth doing before the source list changes much;
recorded here so the reason it wasn't done today is on record rather than
rediscovered.

## Checked and found sound

- **`dbipLiteIpv6`** — switching it off cannot strand IPv6 rows: the
  ingester truncates the whole table before reinserting, rather than
  deleting per-source.
- **`ipIntelMode`** — a config/reality mismatch is detected, logged, and
  deliberately *not* auto-converted; changing form requires
  `ip-insight flatten --mode <x>` by name. Correct as designed.
- **Geofeed collapse floor** — `replaceGeofeedRows` refuses to apply a
  run returning under 50% of the previous row count, leaving existing
  data in place. A real guard against exactly the "upstream broke and we
  wiped good data" failure.
